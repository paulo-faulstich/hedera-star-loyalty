Three primitives

What the prototype demonstrates

1%

Custom fees enforced by consensus

A CustomFractionalFee attaches to the token, not to a contract. Every third-party transfer routes 1% to the merchant automatically. The fee is part of the protocol message, settled by the network.

Audit log you don't have to build

Every reward and redemption emits a JSON event to a Hedera Consensus Service topic. Messages get a global consensus timestamp and a monotonic sequence number. The audit log is the chain.

Granular governance via capability keys

A token can carry seven optional keys: admin, supply, freeze, kyc, wipe, pause, feeSchedule. Each can be a different signer. Unset keys are permanently absent.

Walkthrough

How it works, step by step

  1. 1

    The brand mints the token

    10,000 tokens, fungible, 6 decimals, finite supply, treasury = merchant. feeScheduleKey set so the fee schedule can be updated later.

  2. 2

    The brand attaches a 1% royalty fee

    TokenFeeScheduleUpdateTransaction with a CustomFractionalFee (1/100, inclusive, collector = merchant). Fee logic lives in token metadata, not in client code.

  3. 3

    The customer associates the token

    Hedera requires explicit opt-in to receive an HTS token (TokenAssociateTransaction), signed by the receiving account. It is the protocol-level anti-spam mechanism.

  4. 4

    Reward triggers a fee assessment

    Operator sends tokens to the customer. The network assesses the 1% fee and credits the merchant in the same transaction. record.assessedCustomFees proves it.

  5. 5

    The event lands in the audit log

    TopicMessageSubmitTransaction writes a JSON event with sender, receiver, amount and assessed fees. The dashboard reads it back from the mirror node seconds later.

Architecture

Browser writes through a server. Reads bypass it.

Private keys live on the local Node server, never in the browser. Writes are authenticated; reads hit the public mirror node directly, the same separation any real loyalty backend would have.
